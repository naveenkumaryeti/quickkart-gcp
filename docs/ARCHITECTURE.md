# Architecture and concepts
**Tiers:** (1) frontend MIG: nginx serves static UI and proxies `/api` to the backend internal LB; (2) backend MIG: Flask API + Pub/Sub consumer (service `quickkart-worker`, off by default); (3) Firestore, Cloud Storage, Pub/Sub, Logging, Monitoring.
## Consistency design
1. **Order creation** = one Firestore transaction: idempotency check (order id = hash(customer, Idempotency-Key)), product validation, stock decrement, order, tableService, tableQueue, outbox event. Never oversells, never double-decrements.
2. **Pub/Sub** is outside Firestore: after commit the event is published and the outbox row set to PUBLISHED. If that fails the order stays safe, the outbox row stays PENDING, and `reconcile()` (worker every 30 s / Admin button) republishes. Duplicates are possible (at-least-once) -> consumer is idempotent (tableQueue already Processed -> ack).
3. **Consumer** pulls, validates, runs a Firestore transaction (order Processing + tableService + tableQueue Processed), **acks only after success**; failures are NACKed, retried with backoff (10-60 s), and after 5 deliveries Pub/Sub dead-letters them; the DLQ drain marks tableQueue `Failed`.
4. **Cloud Storage copies** (`products/<id>.json`, `orders/<id>.json`) are uploaded with an object-generation precondition; a version-checked transaction clears `gcsSyncPending`; leftovers are repaired by `reconcile()`.
## Concepts (for the class)
- **Service account**: identity for software; has an email, no password. **Human user**: person with a login. **Why a backend needs one**: so IAM can grant exactly what it may do and Cloud Audit Logs show who did it.
- **Attached service account + ADC**: the VM is created with a service account; client libraries call the metadata server (169.254.169.254) and get short-lived tokens automatically (ADC finds them). No key file exists; locally ADC uses `gcloud auth application-default login`.
- **vs Azure Managed Identity**: same idea. GCP service accounts are separate IAM principals that you create and attach (many VMs can share one; roles are granted to its email); Azure system-assigned identities are created with and bound to one resource. The GCP equivalent of a *user-assigned* identity is closest.
- **Why JSON keys are dangerous**: long-lived, copyable, leak via git/logs, hard to rotate/attribute. We create none (`gcloud iam service-accounts keys list --managed-by=user` is empty).
- **IAM**: who (principal) + what (role = permission set) + on which resource (scope). **Least privilege**: only needed roles on the narrowest resource. **Predefined vs custom roles**: Google-maintained vs your own permission list (use when a predefined role is too broad).
- **Pub/Sub**: topic (where publishers send) -> subscription (a queue of copies for a consumer). **Pull** = consumer asks; **push** = Pub/Sub calls an HTTPS endpoint. **Ack**: tells Pub/Sub the work is done; unacked messages are redelivered. **At-least-once** delivery -> idempotent consumers. **Retention**: unacked messages kept 7 days. **Dead-letter topic**: parking place after max delivery attempts.
- **Firewall vs NSG/ASG**: GCP firewall rules are VPC-wide, stateful, prioritized; targets are *tags* or *service accounts*. Tags are labels anyone with instance-edit rights can set; service-account targeting is identity-based (stronger) and is what we use frontend->backend. Neither is an exact ASG: an ASG is an Azure resource referenced in NSG rules; GCP has no such object.
- **VPC vs subnet**: VPC is global; subnets are regional. **Private Google Access**: VMs without external IPs reach Google APIs. **Cloud NAT**: outbound-only internet (apt/pip). **Private Service Connect**: private endpoint for Google APIs/services (optional upgrade, not required here).
